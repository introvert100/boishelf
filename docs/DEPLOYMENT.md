# Deploy Read and Rich

## 1. Apply the database migration

Back up the Supabase project. Apply every unapplied file in `supabase/migrations/` in filename order. The existing store already has `20261017102902_mixed_bundles.sql`, which backfilled bundle/order member formats. The subsequent **single-format-only** update needs no new migration: the application rejects mixed saves and orders and hides old combined offers. Existing order snapshots remain available for fulfillment. Do not remove or rerun historical migrations, or mix SQL Editor and CLI migration history blindly.

For the Admin payment-settings release, apply `20261020103721_admin_payment_settings.sql` **before deploying the application**. It creates one service-only settings row; existing orders and claims are unchanged. Verify RLS and service-role select/update grants, with no `anon`/`authenticated` grants. A missing migration or settings read failure stops checkout rather than falling back to an obsolete receiving number.

Verify RLS on `print_editions`, `bundles`, `bundle_members`, `order_items`, `order_item_members`, `order_shipping`, `fulfillment_events`, and `inventory_events`. The `ebooks` and `covers` buckets remain private. Run `npm run db:test` locally before deploying.

For district delivery and payment controls, apply `20261027160200_district_delivery_checkout_controls.sql` **before deploying**. It creates service-only `delivery_districts`, seeds only Dhaka using its existing fee (50 BDT for a fresh setup), adds audited payment controls, and updates the atomic physical-order RPC. Empty district lists close printed checkout. Removed districts reject new orders; saved order fees and retry snapshots remain unchanged. Do not deploy the app until this migration reports success. Old app code still uses the legacy two-zone rates, so complete the deployment promptly after migration; do not leave that version serving checkout.

## 2. Configure existing services

Keep the existing Supabase URL, publishable key, server secret, Gmail OTP/Brevo SMTP, Turnstile, `ADMIN_EMAIL`, support email and monitor token settings. Use `render.yaml` for the existing `boishelf` web service; its internal service name remains unchanged. Payment switches now live in **Admin → Payments**, not Render. `BKASH_BUSINESS_ACCOUNT_CONFIRMED` and `COD_COURIER_CONFIRMED` bootstrap attestations only until an Admin choice is saved. Remove unused `MANUAL_BKASH_ENABLED` and `COD_ENABLED` after release; they no longer pause checkout. Remove obsolete `PAYMENT_MODE`, `SSLCOMMERZ_*`, `LIVE_PAYMENTS_*`, `MERCHANT_APPROVED` and `PAID_HOSTING_CONFIRMED` variables after release.

Use a bKash **Personal Retail or Merchant** account for receiving customer payments. bKash says its [personal app is for personal use](https://www.bkash.com/en/page/terms-of-use-bkash-app), while its [Personal Retail Account](https://www.bkash.com/en/page/personal-retail-account) can receive customer payments without this store calling a payment API. Do not put a personal receiving number into checkout.

After deployment, open **Admin → Payments**, enter the eligible 11-digit receiving number and click **Save bKash number**. Refresh and verify it remains saved. `BKASH_RECEIVE_NUMBER` in Render is an optional bootstrap fallback until the first Admin save; the saved setting then takes precedence without redeploying. Existing and retried orders keep their original number. Confirm the exact payment method with bKash and test it yourself. Publish real books and your final Privacy, Terms, Refund, Copyright, and Shipping policies in Bangla and English. For printed sales, configure allowed districts and individual fees in **Printed & delivery**, actual on-hand stock, and a COD-capable courier arrangement. In **Payments**, confirm the eligible business account/courier, set the payment switches, and save. Inspect the availability status and finish every missing policy/stock/number requirement. The migration requests both switches on as the owner instructed, but does not fabricate business or courier attestations. Verify a controlled COD delivery and a real bKash transfer/review/download. Saving a number or a switch does not bypass the other readiness gates.

## 3. Connect readandrich.com

`render.yaml` adds the **root** `readandrich.com` to the existing service. In Render → service → Settings → Custom Domains, check it appears or add it there if the Blueprint has not synced. Root registration makes Render redirect `www` to the root.

**Check the domain's authoritative nameservers before editing DNS.** As of 14 October 2026 they are Namecheap (`dns1.registrar-servers.com` and `dns2.registrar-servers.com`), and the root A record resolves to Render's `216.24.57.1`. In Namecheap → Domain List → **Manage** → **Advanced DNS**, keep `A` host `@` → `216.24.57.1` and `CNAME` host `www` → `boishelf.onrender.com`; remove conflicting records and `AAAA` records. Render verifies the domain and redirects `www` to the root. Follow [Render's Namecheap DNS instructions](https://render.com/docs/configure-namecheap-dns). If authoritative nameservers are changed back to Cloudflare, edit DNS there instead: use `CNAME` `@` and `www` → `boishelf.onrender.com`, both **DNS only** until Render issues certificates, with Cloudflare SSL/TLS mode **Full**, following [Render's Cloudflare instructions](https://render.com/docs/configure-cloudflare-dns).

When HTTPS works, set Render `NEXT_PUBLIC_APP_URL=https://readandrich.com` under **Environment** and redeploy. A 403 from a same-origin checkout request indicates this value is still the old address. In Supabase → Authentication → URL Configuration, set Site URL to `https://readandrich.com` and add any exact production callback/redirect URL used by the email template or app; retain the old Render URL temporarily during transition. In Cloudflare Turnstile, add `readandrich.com` and `www.readandrich.com` to allowed hostnames and retain the Render hostname during transition. Change the Supabase email-template subject/body to **Read and Rich** while keeping `{{ .Token }}`. Test a Gmail code end to end. See [Supabase redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls) and [Turnstile hostnames](https://developers.cloudflare.com/turnstile/additional-configuration/hostname-management/).

## 4. Verify the live flow

Check `/api/health` and the authenticated `/api/health/ready` monitor. Sign in with a Gmail code. Create one small real order: the site must show the exact BDT amount, receiving number and order reference. Pay in bKash, submit the transaction ID and sender-number last four digits. The order must remain **under review** and the download endpoint must deny access. Compare recipient, amount, transaction ID and reference in your bKash account; approve in `/admin` → **Orders**. Only then should PDF/EPUB appear in My Library and download successfully.

Also test a rejected claim and resubmission, duplicate transaction ID, a second customer, sign-out, mobile/keyboard use, and 200% zoom. Do not claim instant delivery: approval depends on you checking the transfer. Monitor the Admin queue and failed request IDs. The free Render service can sleep and has limited capacity; plan reliable hosting and backups before promising response times.

Test a printed-only book, printed bundle, and ebook bundle. Confirm mixed offers and mismatched member formats are rejected. Check cart totals for each configured district and an unavailable district, out-of-stock rejection, order retry, cancellation/restocking, COD collection, bKash approval, and ebook entitlements. Printed bundles use delivery checkout; ebook bundles unlock only after verified bKash approval. Check customer address isolation, homepage landing after login, and library refresh. Run `npm run check`, `npm run validate:render`, `npm run test:e2e`, and `npm run test:e2e:ui`.

## Rollback

Turn off both payment switches in **Admin → Payments** and save to stop new orders. If Admin is unavailable, execute `update public.payment_settings set bkash_enabled=false,cod_enabled=false where id='default';` from the privileged Supabase SQL Editor. Keep order status and Admin review available for existing orders. Before rolling back to code from before mixed bundles, unpublish mixed bundles and finish or reconcile their payments/fulfillment using the new code. Older code does not understand mixed orders. Preserve the migration, snapshots, and orders; restore a tested backup only if the database itself is damaged.

Before rolling back to code that reads only `BKASH_RECEIVE_NUMBER`, align that environment value with the number saved in Admin. Leave the settings table and existing order payment instructions in place.
