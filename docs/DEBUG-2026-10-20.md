# Bundle selection and manual payment settings

## Failure and reproduction

The owner reported on 20 October that books could not be selected in Admin bundles. No new production request ID or log was supplied. Missing editions correctly disabled selection, but the editor had no direct setup action. Inspection also found that printed-edition saves changed only the single `recentBook` state and did not refresh the server catalogue. Preparing another book replaced that state, so the first book appeared to lack its printed edition again until reload.

The isolated `/admin-editor` fixture reproduces the state problem with an intentionally stale server snapshot: start a printed bundle, set up each of two books, return, then select both. Before the fix the first checkbox becomes disabled after saving the second book. The regression failed at that checkbox. The fix retains per-book printed price/stock edits, refreshes after the server confirms a save, and keeps the unfinished bundle mounted while navigating to setup. Missing editions, unpublished/sample books and archived books remain blocked with a reason and a setup action.

## Payment behavior and security

The existing buyer claim and atomic owner-approval workflow is reused. New owner-only `/api/admin/payments` GET/POST handlers read/save the receiving number through `payment_settings`. The new migration enables RLS, revokes public/customer grants, and grants only server select/update. Saves validate an 11-digit Bangladesh number and record the owner/time. Origin checks and rate limits remain in place. No service keys, transaction details or private paths are logged.

Before the first Admin save, the existing valid Render number is the bootstrap value. After a save the database number takes precedence for all new ebook, bundle and printed-bKash checkouts. A settings read error throws instead of reverting to an older number. Existing and retried orders retain their original number snapshot. Buyer pages add copy-number feedback and explicit awaiting-approval status. Review copy distinguishes ebook access from printed delivery; approval requirements and launch gates are unchanged.

## Validation and rollout

Validated locally with Node 24: `npm run typecheck`, `npm test` (55 passing tests), `npm run build`, `npm run test:e2e` (14 desktop/mobile checks), and `npm run test:e2e:ui` (16 desktop/mobile checks). The isolated browser tests exercise two-book setup, single-format saves, owner/non-owner/anonymous API access, origin rejection, invalid numbers, save/reload, copying the original order number, submission and owner approval/rejection. Screenshots are saved under ignored `test-results/`. The 200% zoom check revealed wrapping problems; the payment form now has its own grid and header/Admin tabs wrap. Browser tests use synthetic data only. A sandbox restriction on Windows junction creation required running the build outside the sandbox; application code compiled successfully.
